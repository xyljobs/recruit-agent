# 智聘Agent · GOAI 无界应用赛道参赛说明

> 赛道：无界应用 Boundless Agents ｜ 提交截止：2026-08-16 ｜ 许可：Apache-2.0

## 一、一句话定位

智聘Agent 是一款可私有部署的 AI 招聘决策智能体系统：面向**工业制造**与 IT 外包等人力密集行业的人才供应链场景，把"JD 解析 → 候选人匹配 → 短名单决策 → 沟通准备 → 结果复盘"做成完整闭环；四个协作智能体（解析/匹配/沟通/数据工具）加一个人类决策节点协同，并用 AI 执行边界治理把模型能力关进制度的笼子——默认纯规则运行，AI 按需、按审批、按去标识化解锁。

## 二、目标用户

- 制造业企业（整车/零部件/电子装配）的招聘团队：产线工程师与技工招聘，招工周期紧、到岗流失率高
- IT 行业人力外包公司的招聘团队（单岗位简历筛选 4-6 小时、有效匹配率仅 40-50% 的重人力场景）
- 企业 HR 部门的技术岗位招聘
- 对数据出境与候选人隐私有强合规要求、无法使用公有云 SaaS 的组织（私有部署是硬需求）

## 三、场景痛点

以下痛点数据基于对 5 家人力外包公司 HR 的深度访谈测算（标注为测算值，实测数据见"效果验证"一节的持续校准机制）：

1. 简历搜索耗时：HR 在招聘平台手动搜索筛选，单岗位 4-6 小时。
2. 匹配准确率低：关键词匹配流于表面，人工筛选易疲劳，有效匹配率 40-50%。
3. 沟通效率差：群发模板消息响应率 15-20%，个性化沟通人力成本高。
4. 重复劳动：每个岗位重复"搜 → 筛 → 聊"，无法规模化。
5. 合规风险：简历数据散落在个人电脑与聊天工具中，缺乏授权留痕与撤回机制。
6. 制造业人才缺口：产线工程师/技工招工潮期简历量大，HR 读不懂 PLC/工业机器人技能栈，依赖车间主任逐份筛简历。

## 四、完整闭环（七要素对照）

| 闭环要素 | 系统实现 |
|----------|----------|
| 用户输入 | JD 文本、简历文件（含扫描件）、搜索条件、ATS/CSV 导入 |
| 任务理解 | JD 解析 LLM 结构化提取，含隐含需求识别（"抗压能力强"→话术强调成长空间等） |
| 流程编排 | 解析→规则预筛+LLM 深度分析→短名单→逐条人工决策→沟通 brief→状态跟进→结果复盘 |
| 知识/工具调用 | 本地知识库分块检索（IT 技能图谱、话术模板库）；Boss 直聘本地 Worker、ATS 写回 Worker、简历批处理 Worker |
| 结果交付 | 可解释匹配报告（证据/缺失信息/置信度拆解）、短名单、沟通话术、HTML 候选人报告、决策看板 |
| 异常处理 | 任务队列状态机（error/login_required 恢复）、租约防并发、rules_only 自动降级、启动缺表校验、出站主机白名单 |
| 效果验证 | outcomes 结果事件 + calibration 校准：真实招聘结果回流，持续校准评分权重；`pnpm eval:match` 提供离线排序一致性评测 |

关键设计：AI 分数只参与排序，不产生决策。自动拒绝、发 Offer、录用均不存在；短名单逐条由 HR 决策并留痕，沟通 brief 仅在人工"已接受"后生成。

## 五、数据来源

1. 企业自有简历库：官网投递、内推、招聘会等官方渠道获取的授权简历（CSV/JSON 基线导入，入库前敏感字段加密）。
2. 候选人主动授权：录入时记录授权范围与时间；授权撤回触发最强清理并生成回执。
3. 部署方自有招聘平台账号：Boss 直聘搜索由 HR 本人扫码登录、本地 Worker 执行，系统不集中存储平台凭证（详见合规白皮书）。

## 六、隐私保护（摘要，全文见《数据合规与隐私白皮书》）

- 存储加密：姓名/邮箱/电话/公司/职位 AES-256-GCM 加密，HMAC 索引支持精确查询而不暴露明文。
- AI 执行边界：`rules_only`（默认）/ `private_endpoint` / `approved_cloud` 三档；云端模式仅发送去标识化载荷（无姓名、联系方式、公司、原始简历），且需部署级 + 租户级双重审批。
- 候选人权利：知情授权、拒绝自动化匹配、撤回授权、决策权配置、权利请求处理 API。
- 出站治理：ATS 写回目标主机精确白名单，为空全拒。

## 七、行业边界

- 系统定位是"决策副驾驶"而非自动决策器：不替代 HR 做拒绝/录用决定，规避《个人信息保护法》第 24 条自动化决策风险；自动化辅助需完成影响性评估（PIA）证据链方可启用。
- 不做跨企业数据聚合：私有部署、数据不出域，每个组织独立租户（RLS 隔离）。
- 招聘平台接入遵循"人授权、本地跑、可审计"，并预留官方 API 接入位。

## 八、技术架构（智能体拓扑）

```
人类决策节点（HR）── 接受 / 覆盖 / 补充理由（留痕）
        │
编排层 Next.js 16（App Router, TypeScript strict）
  ├─ JD 解析 Agent：LLM 结构化提取 + 隐含需求识别 → 需求卡片
  ├─ 匹配 Agent：规则预筛 explainable-base-v1 + LLM 深度分析
  │              → 证据 / 缺失信息 / 版本化置信度拆解
  ├─ 沟通 Agent：本地知识库（IT 技能图谱 + 话术模板库，含制造业话术）
  │              → 个性化 brief（仅在人工"已接受"后生成）
  └─ AI 网关 AiExecutionGateway：rules_only / private_endpoint /
                 approved_cloud 三档 + 去标识化 + 租户级双重审批
数据与工具 Agent（Python/uv，部署方机器；任务队列 + 租约 + 状态机）
  ├─ 搜索 Agent（boss_worker）：部署方自有账号外部寻源
  │        状态机 pending→running→done/error/login_required，租约防并发
  ├─ 简历解析 Agent（resume_batch_worker）：批处理入库，
  │        扫描版 PDF 视觉结构化（多模态，默认关闭、授权后启用）
  └─ 写回 Agent（integration worker）：ATS 出站写回，
           outbox 事务解耦 + 目标主机精确白名单
状态与证据层 Supabase（PostgreSQL, RLS, 可 Docker 自托管）
  └─ 结果事件追加只读、calibration 校准回路、决策指标看板
```

每个 Agent 的执行痕迹（任务状态流转、租约认领、outbox 投递、人工覆盖理由）均持久化为可审计证据，构成大赛所强调的"执行证据沉淀"。

## 九、多模态能力

简历批处理流水线支持扫描版 PDF：视觉模型（默认 `qwen-vl-max`，可配私有端点）将扫描件转为结构化简历后进入同一匹配闭环。该能力默认关闭（`ALLOW_EXTERNAL_RESUME_BATCH_ANALYSIS=false`），需管理员显式开启——与"候选人授权后显式启用"的隐私设计一致。文本类简历走本地解析，不依赖外部模型。

## 十、可复制性

- Apache-2.0 开源，无平台绑定：Next.js + Supabase，官方云或自托管均可。
- 一键部署：`docker compose up --build` 起全栈；`pnpm db:migrate && pnpm admin:bootstrap && pnpm seed:demo` 初始化演示环境。
- 质量门禁随仓库交付：74+ 单元测试、数据库集成测试（迁移幂等/RLS/决策流程/100 候选人性能包络）、Python Worker 测试、GitHub Actions CI。
- 项目来源披露：前身为团队 2025 年火山杯参赛原型（初版基于 Coze 搭建）；当前仓库为同一团队完全重构迭代（去平台 SDK、自托管架构、新增执行边界治理/决策留痕/复盘校准），代码全部自研，无许可兼容问题，详见 README「项目来源与已有基础」。

## 十一、效果验证

- 真实数据评测（2026-08，详见 `docs/评测报告_2026-08.md`）：1 个真实在招职位 + 20 份真实授权简历（去标识编号 R01-R20），资深招聘方按"强推/可谈/不推"三档标注作为人工基准。规则评分器与人工排序的 **Spearman 秩相关 0.706**，**强推候选人零漏出前 10（召回率@10 = 4/4）**。分歧样本（关键词高分被人工否决、综合功底被关键词漏判等）均指向"结构化字段之外的判断"，反向验证了"AI 只排序、人决策"的设计与校准回路的必要性。基准文件随仓库交付，`pnpm eval:match scripts/match-benchmark.java-real.json` 一键复现。
- 运行证据：`docs/evidence/` 收录 Boss 搜索任务队列真实状态机日志（脱敏）、质量门禁原始输出（validate + 74 单元测试 + 数据库集成测试 + 25 个 Python Worker 测试全绿）。
- 离线评测工具：`pnpm eval:match` 对比系统基础分与人工基准排序，输出 Spearman 秩相关与 Top-K 命中率（样例基准随仓库交付，可复现）。
- 在线校准：outcomes 记录触达/回复/面试/录用/撤回等真实事件；calibration 按队列对比推荐与结果，生成权重校准建议，经管理员批准后生效（版本化、可回滚）。
- 看板诚实性：零分母显示"待积累"，不使用平均模型分冒充业务结果。

## 十三、Agent 设计自证（模块职责 / 输入输出 / 决策逻辑 / 工具调用）

按大赛"Agent 与 workflow 之辨"的口径逐模块自证：关键不在 LLM 调用次数，而在是否形成任务理解、流程编排、工具调用、多轮交互与结果交付的闭环。

| 模块 | 职责 | 输入 | 输出 | 决策逻辑 | 工具 / 外部依赖 |
|---|---|---|---|---|---|
| JD 解析 Agent | 非结构化 JD → 结构化需求卡片，识别隐含需求 | JD 文本 | 需求卡片（技能/经验/学历/隐含需求/完整度/缺失字段） | rules_only 走规则提取；启用模型时 LLM 提取 + schema 校验，失败自动回退规则 | LLM（可选）、本地技能图谱 |
| 匹配 Agent | 可解释排序与证据生成 | 需求卡片 + 已授权候选人 | 四维评分、证据快照、缺失信息、版本化置信度 | 规则预筛 explainable-base-v1 恒跑；LLM 深析仅批准档运行、失败回退；分数只排序不决策 | LLM（可选）、知识库检索 |
| 沟通 Agent | 个性化沟通 brief | 人工"已接受"的短名单条目 + 证据 | brief / 话术（禁决策性表述） | 仅在人工接受后触发；rules_only 走规则模板，启用模型时知识库增强生成 | 本地话术模板库、技能图谱 |
| 数据工具 Agent（搜索/简历批处理/写回 Worker） | 外部寻源、批量解析入库、ATS 写回 | 任务队列任务（含租约） | 状态流转、HTML 报告、写回结果 | 自主状态机 pending→running→done/error/login_required，租约防并发、失败可恢复；不依赖 LLM 调度 | 部署方自有 Boss 账号本地浏览器、pdfplumber/PyMuPDF、出站主机白名单、钉钉 MCP（可选） |
| AI 网关 AiExecutionGateway | 执行边界治理 | 部署模式 + 租户审批 + 载荷 | 放行 / 去标识化 / 降级决策 | 三档上限 + 租户逐项审批 + 去标识化，未批准自动降 rules_only | 无（纯治理层） |
| 人类决策节点（HR） | 短名单逐条接受/覆盖/补充理由 | 可解释短名单 | 决策留痕，触发下游沟通与校准 | 人 | 无 |

**为什么是 Agent 而非多段 prompt 串联的 workflow：**

1. 自主执行与异常分支：数据工具 Agent 拥有独立状态机、租约认领、失败重试与 login_required 恢复，执行痕迹持久化为可审计证据（见 `docs/evidence/` 真实状态机日志），不是请求内的一次性函数调用。
2. 多轮交互且跨任务闭环：HR 在短名单上逐条接受/覆盖/补理由构成任务内多轮；outcomes 真实招聘事件经 calibration 回流校准评分权重，构成跨任务反馈闭环（版本化、可回滚）。
3. 工具调用超出文本生成：本地知识库分块检索、任务队列、浏览器 Worker、精确白名单出站写回——LLM 只是可选的能力档之一，rules_only 下闭环依然完整。
4. 结果交付可操作可追溯：短名单、证据快照、brief、决策看板均带版本与留痕，输出可解释依据而非仅文本。
