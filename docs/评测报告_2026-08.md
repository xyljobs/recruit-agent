# 匹配评分基准评测报告（2026-08）

> 复现命令：`pnpm eval:match scripts/match-benchmark.java-real.json`
> 评测对象：规则评分器 explainable-base-v1（`src/lib/matching/scorer.ts`，与线上单人/批量匹配共用同一确定性评分函数）。

## 一、方法

- **职位**：真实在招 Java 职位（阿里云数据库/中间件管控接口扩展开发，5 年以上，Spring Boot/Spring Cloud/MyBatis/Redis/MQ/JVM，北京/杭州，每月出差上海一周）。
- **候选人**：20 份真实授权简历，结构化提取后**去标识化**（不含姓名、联系方式、公司名，编号 R01-R20），基准文件随仓库交付。
- **人工基准**：由资深 IT 招聘方按三档标注——强推 4（R01/R02/R05/R07）、可谈 4（R03/R04/R06/R08）、不推 12。
- **指标**：Spearman 秩相关（并列档用平均秩）；强推召回率@K（人工强推档在系统前 K 名的覆盖比例，避免 Top-K 在并列档下的任意截断）。

## 三、分歧分析

1. **R16（系统第 3，人工不推）**：技能关键词覆盖高（skill 88），但人工基于结构化字段之外的判断（项目深度、简历质量等）否决。这正是"关键词覆盖 ≠ 人岗匹配"的典型样本。
2. **R01/R02（人工强推，系统第 6/8）**：综合功底被人工认可，但简历未显式出现 JVM/MQ 关键词，规则评分按证据保守计分。
3. **R03（人工可谈，系统第 11）**：11 年经验但现居武汉且意向武汉，系统按单城市地域规则重罚；而 JD 实际允许北京/杭州双地，标注方保留了弹性。

## 四、结论

- 规则评分器与资深招聘方排序一致性 0.706，且**强推零漏出前 10**，胜任"证据排序"职责。
- 分歧样本均指向"结构化字段之外的判断"，验证了产品核心设计：**AI 只排序不决策**，短名单逐条人工决策并留痕；分歧样本同时作为 calibration 校准回路的输入，驱动权重版本化调整。

## 五、局限

- 单职位、单标注方、三档粗排；未做跨标注者一致性检验。
- JD 未写薪资，薪资维度未参与区分；地域按单城市计分，与双地 JD 存在口径差。
- 决赛前计划：扩展至 3 个职位（含制造业）、60 份简历、双标注者，替换本基线。
